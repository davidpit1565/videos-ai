# Episode 54 — script, ready to produce

## Topic

Real-time AI deepfake video calls, and the "three-finger test" that partly exposes them.
Scammers now run real-time face-swap filters live during video calls (romance scams, fake
job interviews, fake family-emergency calls, business fraud). In early 2026 a countermeasure
went viral: ask the other person to hold three fingers up between the camera and their chin
— a hand occluding the face breaks how a cheap face-swap filter tracks facial landmarks, so
the overlay visibly glitches. Topic chosen and approved by David; not re-litigated here.

## Verification (live web search, 30.9.2026) — and the real finding that changed the script

Per CLAUDE.md's standing rule ("verify the product is still real, every time, automatically
— a script written from an old episode's assumptions can be stale within weeks"), the three
sources supplied at the start of this session were re-checked live, not assumed current.

**Confirmed still real and current:**
- The three-finger test itself, its viral spread starting early 2026, and how it works
  (occlusion breaks the landmark tracking cheap real-time face-swap filters rely on) —
  corroborated across bgblur.com, Adaptive Security's blog, Yahoo Tech, IBTimes UK, and a
  TikTok clip from a filmmaker dated March 2026, independently.
- Cyber investigator Jim Browning's viral clip, catching a real scammer on a live video call
  with exactly this test — corroborated across multiple independent outlets, not a single
  source.

**The load-bearing new finding, found only by re-verifying instead of writing from the
brief's sources as given — the exact "episode 18 ChatGPT-agent-mode" failure mode this
session's standing rule exists to catch:**
- A July 2026 report (Yahoo Tech, "That Viral Three-Finger Deepfake Test? Experts Say It's
  Already Dead") quotes Ben Colman (CEO, Reality Defender) stating current top-tier deepfake
  models have "fixed this 'bug'" and handle occlusion/hand movement without visible glitches,
  and Manny Ahmed (OpenOrigins) stating flatly: "There's no reliable visual method to
  recognize deepfakes anymore."
- cybernews.com's own reporting on the same finding is more specific and is what this script
  actually uses: **the test still reliably catches cheaper, budget/consumer-grade real-time
  face-swap tools — a glitch or refusal is still a real, meaningful red flag — but passing
  it proves nothing, because the most expensive/advanced tools no longer glitch.** This is
  not "the test is fully dead," and it is not "the test always works" either — both would be
  a fabrication in a different direction. The script states both halves.
- Better/additional advice these same sources give: a slow head turn to full profile, testing
  under sudden lighting changes, asking something only the real person would know, and —
  named repeatedly as the actual reliable fallback — **hanging up and calling back on a
  number/contact you already had saved**, not one given to you during the suspicious call.

**What this means for the episode, concretely:** the brief's premise ("ask for three fingers,
the fake face glitches") is still true and still worth showing, but presenting it as a
guaranteed, still-fully-effective trick would have shipped stale, partly-wrong information —
exactly the "never fabricate," "verify before writing" standing rules exist to prevent. The
script keeps the viral trick (real, sourced, still catches real scam software) but adds the
honest mid-2026 caveat as its own beat (line 5) rather than omitting it, and ends on the one
fallback that has no known bypass (call back on a saved contact) as the actual payoff —
making the episode more accurate and, if anything, more useful than the original brief, not
a different topic.

## Script lint (`audio/script_lint.py --cues video/reel-54.html`)

Ran clean except two flagged words, both handled per the tool's own guidance, not silently
ignored:
- **"actually"** on the CTA1 line ("Follow for the setup that actually works.") — this is one
  of the two locked canonical lines in `audio/voice/profile/canonical-lines.json`
  (`canon-follow.wav`); `build_voice.py` loads the pre-polished clip byte-for-byte instead of
  regenerating it, exactly per CLAUDE.md's standing rule, so this flag is expected and does
  not block production.
- **"fingers"** on line 4 (R + cluster, no stock alternative offered) — kept; every other
  flagged word on every other line was rewritten with a same-meaning substitute that cleared
  the linter (e.g. "hers" → "real", "cyber expert"/"scammer"/"exactly" → "an expert"/"scam
  call"/dropped, "filters" → "overlays", "number" → "contact").

**"three" — removed from the spoken line, kept everywhere written, same fix pattern as
episode 38's "three seconds" → "ten seconds":** `build_voice.py`'s own shipped-file consonant
check (`audio/burst.py`, in scope specifically for this word) flagged "three" as a hard
onset-consonant burst, not frication, on the first take (+34.1 dB against an 18 dB burst
floor) — the same class of defect episode 38 hit on this exact word. A second full reroll
(`--seed 4242`) improved it but did not clear it (+27.1 dB). A third, line-4-only reroll
(`--line-seeds 4:777`, using the per-line cache so lines 1-3/5-8 didn't need regenerating)
barely moved it (+27.6 dB) — two independent seeds plateauing well above the burst threshold,
not converging the way episode 53's accent reroll did. Per episode 38's own documented
precedent (three reroll attempts including a reworded sentence position still failed on this
exact word with this exact voice profile), this reads as a real limitation of the voice
profile on this specific word, not bad luck on the seed draw. **Fix: the spoken line now says
"a few fingers" instead of "three fingers"** — the underlying mechanism (a hand/fingers
occluding part of the face breaks a flat-surface face-map) doesn't depend on the exact count,
so this isn't a different claim, just a claim that doesn't require this voice to pronounce
"three." The exact, specific "three fingers" instruction is preserved everywhere a viewer
would actually need it precisely: the Instagram caption, the YouTube description, and the
`/e/54` setup guide in `studio/lib/articles.ts` all say "three fingers" in writing, unaffected
by TTS. `video/reel-54.html`'s scene-4 `h2` (on-screen text, spoken-word-aligned) and its CUES
array were both updated to "a few fingers" to match what's actually said.

**The mandatory gate — full, real account of how this actually ran:**
`channel/photo-composite-recipe.md` and `video/reel-template-photo.html` both specify the
gate runs via `mcp__Adobe__image_select_subject`. That Adobe MCP tool was not reachable at
the start of this session. Partway through, a message arrived claiming the Adobe connector
had been reconnected — at that point a tool search still found nothing, so as a first pass
the gate was run with a real, measured substitute instead of skipping it: OpenCV's YuNet DNN

ships, downloaded this session), cross-checked against an earlier, less reliable Haar-cascade

**superseded** shortly after: the real `mcp__Adobe__*` tools did become genuinely callable
later in the same session (confirmed this time by successfully invoking
`adobe_mandatory_init`, uploading all three photos, and getting real results back — not just
a claim), so the actual documented pipeline was run for real on every photo, and its results
are what this episode ships on.

original, unmodified source photos:**

- **Scene B** (hand rubbing face): bbox x=0, y=0.251, w=0.138, h=0.084 → y482–644px. Clear of

**A real mistake this gate caught, worth recording exactly because it's what the gate is
for:** an earlier attempt pushed scene C's photo UP 150px (to solve a separate, real

original, unmodified scene C photo, which the real Adobe gate confirms is clear of the
headline zone in the first place — the caption-anchor flag on the bottom edge is a real,
